要求：
1、直接返回 JSON 结果，不要包含任何分析、解释或说明文字，不要使用 markdown 代码块标记
2、严格按照以下格式生成，run_list 必须包含所有依赖接口（含主接口），按执行顺序排列
3、本步骤只负责编排：确定接口、顺序、参数提取（extract_vars）、预期状态码（expected_status）和必要的 headers。**request_body 留空对象 {} 即可，具体数据值由后续「数据填充」步骤负责**，不要在此填写字段值

重要规则：

1、**动态参数**：如果 URL 或请求体需要从前置接口获取动态值，必须添加 `extract_vars` 字段声明提取路径，并在需要的位置使用 `{{变量名}}` 占位符
   - extract_vars 格式：{"变量名": "JSONPath路径"}
   - 常用路径：`$.run_list[x].response.body.data.token`、`$.run_list[x].response.body.data.id`、`$.run_list[x].response.cookies.sessionid`

2、**expected_status**：每个接口必须标注预期状态码。异常场景（如"密码错误"、"未授权"）必须用对应的 4xx 状态码或通配符（如 `"4XX"`）

3、**注册/登录账号**：账号的用户名、密码等具体值由「数据填充」步骤生成。如果多个注册/登录步骤涉及不同用户，在 api_name 或 description 中标注用户角色（如"注册用户A"、"注册用户B"），数据填充步骤会据此为每个用户生成独立账号并保证注册与登录配对

4、**管理员场景**：如果测试用例涉及管理员操作，必须使用预设管理员账号登录（用户名：__ADMIN_USERNAME__，密码：__ADMIN_PASSWORD__），禁止注册新管理员。管理员登录使用占位符：`{"username": "__ADMIN_USERNAME__", "password": "__ADMIN_PASSWORD__"}`

5、**禁止 JS 表达式**：如 `"a".repeat(200)` 等，必须是纯 JSON 字符串值

6、**多用户场景**：每个注册接口使用不同用户名，在 description 中标注用户角色（如"注册用户A"、"注册用户B"）

7、**异常场景测试的 Token 处理**：
   - 如果测试用例要求使用"伪造Token"、"无效Token"、"过期Token"等测试异常场景（如登出返回401）：
     - 必须在 headers 中**显式指定伪造的 Authorization 值**，例如：`"Authorization": "Bearer fake_invalid_token_12345"`
     - **不要使用 {{token}} 占位符**（这会获取真实Token导致测试偏离）
     - 使用固定的伪造字符串，确保接口返回预期的错误码（401/403等）
   - 异常场景示例：
     ```json
     {
       "run_num": 3,
       "api_name": "用户登出接口（伪造Token）",
       "api_url": "/api/users/logout/",
       "method": "POST",
       "headers": {"Authorization": "Bearer eyJhbGciOiJIUzI1NiJ9.FAKE_TOKEN_CONTENT"},
       "request_body": {},
       "expected_status": 401,
       "description": "使用伪造Token登出，预期返回401未授权错误"
     }
     ```
   - 注意：只有正常流程测试（expected_status 为 200/201 等）才不需要显式设置 Authorization，系统会自动注入真实Token
