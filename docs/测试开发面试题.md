# 测试开发面试题 - 基于项目实战

根据测试用例管理平台、AI Generator Service、API Testing Service 三个项目提炼的面试题。

---

## 一、测试理论与方法

### 1. 测试用例设计

**Q1: 平台中用例优先级分为 P0/P1/P2/P3，请说明各优先级的适用场景。**

参考答案：
- P0：核心功能、冒烟测试、阻塞问题，必须100%执行
- P1：重要功能、主要业务流程，建议执行
- P2：一般功能、次要流程，可选执行
- P3：边界场景、异常处理、UI细节，低优先级

**Q2: 平台支持哪些测试方向？各方向的测试目的是什么？**

参考答案：
- 功能点测试：验证功能是否正常工作
- 业务逻辑测试：验证业务规则是否正确（如密码错误提示、账号锁定）
- 其他测试：边界值、异常、安全测试（如空密码登录、SQL注入）
- 扩展方向：性能测试、安全测试、兼容性测试

**Q3: 用例评审流程是怎样的？评审结果有哪些？**

参考答案：
- 流程：创建者提交 → 评审人查看 → 填写意见 → 选择结果 → 通知相关人员
- 结果：通过（用例状态更新为已评审）、拒绝（返回修改意见）、待定（等待更多信息）
- 规则：不能自评、修改后可重新提交、最新评审状态决定用例状态

---

### 2. 测试执行管理

**Q4: 用例执行结果有哪几种？各自的含义和后续动作是什么？**

参考答案：
| 结果 | 含义 | 后续动作 |
|------|------|----------|
| pass | 通过 | 无需后续处理 |
| fail | 失败 | 需提交缺陷报告 |
| block | 阻塞 | 记录阻塞原因，等待解决后继续 |
| skip | 跳过 | 记录跳过原因（如环境不支持） |

**Q5: 如何计算测试通过率？通过率反映了什么？**

参考答案：
- 计算公式：通过率 = 通过次数 / 总执行次数
- 反映产品质量：通过率低说明产品质量差
- 反映测试覆盖：执行次数多说明测试充分

## 二、接口测试

### 1. API 测试流程

**Q6: API Testing Service 的测试用例生命周期是怎样的？**

参考答案：
```
1. 业务流分析 (/flow)
2. 用例生成 (/testcase/generate)
3. 依赖分析 (/dependency)
4. 数据填充 (/testdata/fill)
5. 用例执行 (/testcase/execute)
6. 结果校验 (/testcase/validate)
```

**Q7: 什么是接口依赖分析？举例说明。**

参考答案：
- 定义：分析执行目标接口前需要调用的前置接口
- 示例：测试"修改用户角色"接口，需要先调用：
  1. 用户注册接口（获取 user_id）
  2. 用户登录接口（获取 token）
- 输出：run_list（按执行顺序排列的接口列表）

**Q8: 如何处理接口间的参数传递？**

参考答案：
- 使用 extract_vars 从历史响应中提取值
- 使用 JSONPath 风格路径：`$.run_list[0].response.body.data.id`
- 使用占位符 `{{user_id}}` 在 URL 和 request_body 中标记
- 自动替换：执行时从历史记录提取并替换

### 2. 参数提取与替换

**Q9: 以下 JSONPath 分别提取什么数据？**

```json
$.run_list[0].response.body.data.id
$.run_list[1].response.body.data.token
$.run_list[x].response.body.results[0].id
```

参考答案：
- 第一条：从第一个接口响应的 body.data.id 提取用户ID
- 第二条：从第二个接口响应的 body.data.token 提取登录令牌
- 第三条：从第x个接口响应的 body.results 列表中提取第一个元素的 id

**Q10: Token 自动注入是如何实现的？**

参考答案：
- 从登录接口响应中提取 token（通过 extract_vars）
- 自动添加到后续接口的 Authorization header
- 格式：`Authorization: Bearer {token}`

### 3. 测试账号管理

**Q11: 测试账号的自动化管理策略是什么？**

参考答案：
- 自动生成唯一账号：时间戳格式 `test_YYYYMMDD_HHMMSS_xxxx`
- 多用户场景：不同用户使用不同账号（用户A、用户B）
- 自动清理：执行完成后自动删除测试账号
- 目的：避免"账号已存在"错误，保证每次执行环境干净

**Q12: 为什么使用时间戳格式的测试账号名？**

参考答案：
- 确保每次执行账号唯一
- 避免"用户已存在"错误导致测试失败
- 便于识别和清理测试数据
- 支持多用户场景区分

---

### 4. 异常处理

**Q13: 什么是可跳过错误？为什么要支持跳过？**

参考答案：
- 定义：某些错误不影响后续执行，可以跳过继续
- 示例：注册接口返回"账号已存在"，登录接口仍可执行
- 配置：`SKIPPABLE_ERRORS = {"注册": ["已存在", "已注册"]}`
- 目的：提高测试容错性，偶发错误不影响整体

**Q14: 模糊状态码匹配是如何实现的？有什么应用场景？**

参考答案：
- 实现：`expected_status: "4XX"` 匹配 400-499 所有状态码
- 场景：异常测试不确定具体错误码时使用
- 示例：测试"未授权访问"，预期返回 401 或 403，用 "4XX" 通配

## 三、AI 测试应用

### 1. AI 辅助测试

**Q15: AI Generator Service 如何生成测试用例？**

参考答案：
- 输入：模块名称、功能点、关联需求、测试方向列表
- 流程：构建输入文本 → 并行处理多个测试方向 → 合并用例 → 标准化格式
- 输出：用例标题、测试步骤、预期结果、优先级、测试类型

**Q16: 为什么采用并行生成策略？有什么优势？**

参考答案：
- 原因：不同测试方向相互独立，无依赖关系
- 优势：大幅缩短生成耗时
- 示例：顺序处理 30秒 → 并行处理 10秒

**Q17: AI 测试用例生成的错误容忍策略是什么？**

参考答案：
- 规则：部分测试方向生成失败不影响整体结果
- 场景1：全部成功 → 返回所有用例
- 场景2：部分失败 → 返回成功的用例 + 记录警告
- 场景3：全部失败 → 返回错误
- 目的：宁可返回部分结果，也不因单点失败导致整体不可用

### 3. 批量推理

**Q19: 同步批量和异步批量的区别是什么？各适用什么场景？**

参考答案：
| 类型 | 特点 | 适用场景 |
|------|------|----------|
| 同步批量 | 等待所有完成才返回 | 小批量（<10个） |
| 异步批量 | 立即返回任务ID，后台处理 | 大批量、耗时任务 |

**Q20: 异步批量任务的状态流转是怎样的？**

参考答案：
```
PENDING（等待）→ PROCESSING（处理中）→ COMPLETED（完成）
                                    ↘ FAILED（失败）
```
- 结果保留1小时后自动清理

    根据 JSONPath 风格路径从历史执行记录中提取值

    if path.startswith("$."):

### 2. 重试机制

**Q37: 如何实现 API 调用的重试机制？**

参考答案：
```python
async def call_with_retry(func, max_retries=3, retry_delay=2.0):
    for attempt in range(max_retries):
        try:
            result = await func()
            return result, None
        except Exception as e:
            if attempt < max_retries - 1:
                await asyncio.sleep(retry_delay)
            else:
                return None, f"API调用失败，已重试{max_retries}次: {str(e)}"
```

**项目中采用的混合策略：**

1. **训练模型生成功能测试用例**

**Q46: 训练模型和通用模型+提示词各有什么优缺点？**

参考答案：

**训练模型：**

| 优点 | 缺点 |
|------|------|
| 输出质量稳定，格式统一 | 训练成本高（数据+计算+时间） |
| 提示词简短，推理效率高 | 灵活性差，改需求需重新训练 |
| 格式解析成功率高 | 更新维护困难 |
| 领域知识内化 | 过拟合风险 |
| 长期使用成本低 | 长尾场景覆盖不足 |

**通用模型+提示词：**

| 优点 | 缺点 |
|------|------|
| 灵活性强，改提示词即可 | 输出质量不稳定 |
| 无需训练成本，启动快 | Prompt Engineering 成本高 |
| 覆盖面广，场景适应性强 | Token 消耗大，推理效率低 |
| 快速迭代（小时级） | 依赖提示词质量 |
| 适合长尾和多样化场景 | 格式解析失败率高 |

**项目中选择混合策略的原因：**

| 测试类型 | 方案 | 原因 |
|----------|------|------|
| 功能测试 | 训练模型 | 场景标准、格式统一、质量要求高 |
| 业务逻辑/边界/安全测试 | 提示词 | 场景多样、需求变化快、需灵活适配 |

---

**Q47: 什么场景适合用训练模型？什么场景适合用提示词？**

参考答案：

**适合训练模型的场景：**
- 用例格式高度标准化
- 用例量大且重复性高（训练成本可摊薄）
- 对输出质量要求高
- 有充足的训练数据
- 场景相对固定，变化频率低

**适合通用模型+提示词的场景：**
- 需求变化频繁
- 场景多样化
- 缺乏训练数据
- 快速验证阶段
- 专业领域测试（通过提示词注入领域知识）

**最佳实践：**
```
核心场景（功能测试）→ 投入训练成本，获得稳定输出
长尾场景（边界、安全）→ 使用提示词，保持灵活性
新场景探索 → 先用提示词验证，成熟后再考虑训练
```
