1. 🔴 严重问题 — 需立即修复 (P0)

Critical 运行时 Bug
1.1 auth_service.py 使用未导入的异常类 → refresh_token() 功能完全不可用
📁 Testbackend/apps/users/services/auth_service.py  |  📍 L114, L119, L122
refresh_token() 方法中使用了 BusinessError 和 NotFoundError，但文件顶部只导入了 ValidationError 和 AuthenticationError。任何调用 refresh_token() 的请求都会抛出 NameError。
# 第15行：只导入了这两个 from apps.core.exceptions import ValidationError, AuthenticationError # 第114行：BusinessError 未导入！ raise BusinessError('Token无效或已过期') # 第119行：NotFoundError 未导入！ raise NotFoundError('用户不存在')
影响: Token 刷新功能完全不可用。用户 token 过期后无法刷新，只能重新登录。
Critical 运行时 Bug
1.2 projects/views/views.py 多处解构不存在的 error 变量 → NameError
📁 Testbackend/apps/projects/views/views.py  |  📍 L203, L221, L238, L258, L345, L290
多个视图函数中直接使用 error 变量，但服务方法返回的是单个值（dict/布尔值），不是 (result, error) 元组，导致 NameError。影响 add/update/remove/batch_update 成员、get_activities、update_role 等 6+ 个 API 端点。
# 第196-206行：add_project_member_view member_data = ProjectMemberService.add_member(...) # 返回 dict，不是 tuple if error: # ← NameError: name 'error' is not defined code = 404 if '不存在' in error else 400
影响: 项目成员管理的全部 CRUD 操作不可用。前端调用这些接口会收到 500 错误。
Critical 安全
1.3 SSE 流式视图中 CORS Origin 绕过白名单校验
📁 Testbackend/apps/testcase/views/ai_views.py  |  📍 L357, L1243, L1264, L1607
多处 SSE 流式响应直接使用 request.META.get('HTTP_ORIGIN', ...) 设置 CORS 头，完全绕过 get_safe_cors_origin() 白名单校验。且同时启用了 Access-Control-Allow-Credentials: true，形成有效的跨域凭据携带漏洞。
# 第357行：origin 直接取请求头，不做白名单校验 origin = request.META.get('HTTP_ORIGIN', 'http://localhost:5174') # 第1243行：直接使用未校验的 origin response['Access-Control-Allow-Origin'] = origin # ← 风险！ response['Access-Control-Allow-Credentials'] = 'true' # 第1264行：DRF 版本用 * 做 fallback response['Access-Control-Allow-Origin'] = request.META.get('HTTP_ORIGIN', '*')
影响: 任意网站发起的跨域请求都可携带用户凭据访问 SSE 流式接口，可能导致 AI 生成结果被窃取。

2. 🟠 高危问题 — 本周内修复 (P1)

High 安全
2.1 管理员凭据被注入到 LLM 提示词中
📁 api-testing-service/app/engine.py  |  📍 L131-132, L257-260, L379-380
TestEngine 将管理员用户名和密码以明文形式嵌入发送到第三方 LLM API 的提示词中。若 LLM 服务商记录提示词数据，管理凭据将泄露。
影响: 第三方 LLM 提供商可能获取到测试系统的管理员凭据，导致权限提升和数据泄露。
High 安全
2.2 知识库全部 API 缺少项目级权限检查
📁 Testbackend/apps/knowledge/views/knowledge_base_views.py  |  📁 knowledge_views.py
知识库创建、编辑、删除、复制、置顶以及所有知识文档（上传、删除、下载、URL导入）操作仅检查 IsAuthenticated，没有验证用户是否为关联项目的成员。任何已登录用户都可以操作任意项目的知识库。
影响: 已认证用户可以跨项目删除/修改其他项目的知识库和文档，造成大规模数据丢失。
High 安全
2.3 用户敏感信息接口无权限控制
📁 Testbackend/apps/users/views/views.py  |  📍 L470-491 (get_user_view)
get_user_view 仅要求 IsAuthenticated，任何已登录用户可查看任意用户邮箱、手机号、最后登录时间/IP 等敏感信息。同理，create_permission_view 等权限管理接口也缺少 @require_system_admin。
影响: 已认证用户可枚举所有用户信息（含隐私数据），并可随意管理系统权限。
High 安全
2.4 密码重置 Token 使用数据库存储而非加密签名
📁 Testbackend/apps/users/services/user_service.py  |  📍 L357-358
密码重置使用 secrets.token_urlsafe(32) 生成的 token 直接存储在数据库中。若数据库泄露，攻击者可提取所有用户的密码重置 token。应使用 Django 内置的 PasswordResetTokenGenerator（基于 HMAC 签名，无需存储）。
影响: 数据库泄露 = 所有用户的密码重置 token 被一网打尽。
High 逻辑缺陷
2.5 ApiTestPermissionService 未过滤已禁用成员
📁 Testbackend/apps/apitest/services/permission.py  |  📍 L17-19
get_user_project_ids() 没有过滤 status='active'，已禁用的成员仍可访问 API 测试用例。而 ProjectPermissionService 中的同名方法正确过滤了状态，存在不一致。
影响: 已被移除或禁用的项目成员仍然可以操作接口测试用例。
High 功能缺失
2.6 知识库文件上传无类型和大小验证
📁 Testbackend/apps/knowledge/views/knowledge_views.py  |  📍 L37-62
知识库文件上传接口仅通过 request.FILES 获取文件并读取内容，没有验证文件类型（无 MIME 检查、无扩展名白名单）、大小限制或恶意内容扫描。
影响: 可上传任意类型和大小的文件（含恶意脚本），可能导致存储耗尽或服务端被攻击。
High 稳定性
2.7 序列化器中递归查询 → N+1 性能黑洞
📁 Testbackend/apps/testcase/serializers/testcase_serializers.py  |  📍 L132-145
TestModuleSerializer._get_all_module_ids() 递归访问 module.children.all()，每次序列化一个模块就触发多次子模块查询。在深层模块树结构下，单次请求可产生数百次数据库查询。
影响: 模块树较深时接口响应时间指数级增长，可能导致超时。
High 代码质量
2.8 900 行超长函数 — generate_test_cases_stream_native
📁 Testbackend/apps/testcase/views/ai_views.py  |  📍 L341-1247
generate_test_cases_stream_native 是一个 ~900 行的巨函数，混合了 SSE 事件生成、知识库检索、AI 生成、向量去重、数据库持久化、错误处理和 CORS 配置。同时与 generate_test_cases_stream（DRF 版本，~350 行）有 ~80% 的代码重复。
影响: 极高维护成本；CORS 处理不一致导致安全漏洞；任何修改都需要在两个位置同步。

5. 🏗 架构风险分析

Medium
5.1 单点故障：Django 是唯一的状态持有者
所有业务数据存储在 Django 的 SQLite 数据库中。两个 FastAPI 微服务只是无状态的 AI/测试执行引擎，依赖 Django 提供数据。一旦 Django 宕机，整个系统不可用。微服务没有独立的降级能力。
Medium
5.2 SQLite 并发瓶颈
生产环境默认使用 SQLite，其写锁机制在高并发下是严重瓶颈。settings.py 中的 check_production_settings() 已正确警告了这一点，但没有强制执行数据库迁移。
Medium
5.3 微服务间耦合度偏高
Django 通过 httpx 同步调用 AI Generator（8001），再通过 SSE 透传调用 API Testing Service（8002）。虽然表面上解耦了，但 Django 的 ai_views.py 中包含大量对微服务输出格式的硬编码假设。如果微服务的响应结构变化，Django 侧就会崩溃。
Medium
5.4 内存任务存储无持久化
AI Generator 的异步批处理任务存储在内存 (TaskStore) 中，每 10 分钟自动清理。服务重启后所有进行中的任务丢失，且没有任何重试机制。
Medium
5.5 Common 模块通过 sys.path hack 注入
common/ 模块通过在每个 FastAPI 的 main.py 中 sys.path.insert(0, ...) 方式注入 workspace 根目录。这不是标准的 Python 包管理方式，打包/部署时容易出问题。
Low
5.6 前端 Vue3 所有路由默认不要求认证
虽然路由守卫在 router/guards.js 中实现了，但 router/index.js 未设置 DEFAULT_PERMISSION_CLASSES，依赖每个路由手动添加 meta.requiresAuth。遗漏的风险始终存在。
Low
5.7 apitest/views/api_testcase.py 中的 CORS 问题
与 ai_views.py 类似，api_testcase.py 第117行和第294行也直接使用未校验的 HTTP_ORIGIN 设置 CORS 头。

7.4 总结

该项目的架构设计思想是好的——分层清哳、异常体系统一、安全配置基线完善。 但在执行层面存在系统性问题：返回值模式不一致导致多处运行时崩溃、权限检查大面积缺失、 CORS 配置多处绕过白名单、代码重复严重。最紧迫的是 5 个运行时 Bug需要立即修复， 以及 .env 中的真实凭据需要立即轮换。

建议按照上述 P0→P1→P2→P3 的顺序逐级修复，每级完成后运行全量测试验证。 修复完成后，应补充集成测试覆盖当前无测试的关键路径（如 SSE 流式 CORS、知识库权限检查）。
