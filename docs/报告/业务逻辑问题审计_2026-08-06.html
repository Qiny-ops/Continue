🔴 严重 (Critical) — 数据安全 + 完整性崩溃

Critical 接口测试
1. 环境凭证明文存储 — 安全漏洞
apitest/models.py ApiEnvironment: auth_token / auth_username / auth_password — 均为 TextField/CharField 明文
API 测试环境的认证凭据（Token、用户名、密码）以明文形式存储在数据库中。序列化器直接暴露这些字段，任何 GET 请求都会返回完整凭据。生产环境 Base URL + Token 的组合被DBA、备份运维、SQL 注入攻击者直接获取。
风险: 攻破测试环境凭据 → 横向渗透生产环境（因为测试/预发布环境往往使用相似凭据策略）
已修复（双层）:
① 存储层：新增 apps/apitest/fields.py，基于 cryptography.fernet 实现 EncryptedCharField/EncryptedTextField；auth_token/auth_username/auth_password 落库为密文（Fernet 对称加密，密钥来自 settings.DB_FIELD_ENCRYPTION_KEY，缺省由 SECRET_KEY 派生）。迁移 0003（字段切换）+ 0004（历史明文凭据重加密，幂等）已生成并应用到开发库，验证 DB 存 gAAAAA… 密文、ORM 读明文。
② 序列化层：读取时脱敏为 ****；并修复回传占位符 **** 会被当成真实凭据覆盖原值的缺陷（create/update 剔除占位符字段）。
③ requirements.txt 加 cryptography==50.0.0；.env/.env.example 加 DB_FIELD_ENCRYPTION_KEY（生产须独立生成并保密）。
Critical 测试用例
2. TestCase.version ≠ TestCase.module.version — 数据一致性无约束
testcase/models/test_case.py: TestCase 同时有 version FK 和 module FK，但模块自己的 version 可能与用例 version 不同
模块属于某个版本，用例也属于某个版本。但没有任何数据库约束或 Python save() 校验保证 case.version_id == case.module.version_id。通过 Django Admin、Shell、或批量更新 API 可以直接创建跨版本的"幽灵用例"——用例在 v2.0，但模块在 v1.0。
风险: 按版本查询时漏掉或用例重复；模块树统计失真；导出报告数据矛盾
修复: 在 TestCase.save() 中检测 module 变化时强制同步 version = module.version；或添加 DB CheckConstraint（PostgreSQL）让 version 成为从 module 派生的计算字段

🟠 高危 (High) — 流程可被绕过 / 操作无防护

High 项目管理
3. Project 状态机完全缺失
projects/models/project.py: STATUS_CHOICES 仅用于展示，无任何状态转换守卫
项目状态（active/completed/pending/archived）可任意转换：已归档的可以"复活"、已完成的可以重新"激活"、pending 可以直接跳到 archived。update_project API 直接把 status 值写入数据库，不做任何校验。
风险: 前端可能对"已完成/已归档"做了 UI 限制，但 API 层面可绕过。已完成项目的用例被人为重新激活修改，审计完整性破坏。
修复: 实现状态机：pending → active → completed/archived（单向不可逆）；update_project 中校验 status 转换合法性
High 接口测试
4. ApiTestCase.status 可手动写入 + 异常路径不更新
apitest/models.py: status 是存储字段且不在 read_only_fields；api_testcase.py: error/断连路径不更新 status
三个独立问题：(a) status 字段可通过 PUT/PATCH API 直接写入，用户可以手动把用例标记为 passed 而不执行；(b) SSE 执行出错（error 事件）只更新 ApiTestRun.result，不更新 ApiTestCase.status；(c) SSE 连接中断时 status 永远停在旧值。
风险: 统计报表不可靠（人为标记"已通过"的用例拉高通过率）；错误/中断的用例显示为旧状态；审计追溯断裂
已修复: ① 序列化器 validate_status 禁止手动写入 passed/failed；② 提取统一 finalize_run() 收口函数，所有 run 结束路径（依赖分析失败 / 执行出错 / SSE 异常中断）均经此更新 status；③ 为 SSE 生成器增加顶层 try/except，连接中断或微服务异常时 run.result='error' 且用例 status 同步为 failed，不再卡在旧值/running。
设计决策: 未将 status 改为从 latest_run 派生的 computed property（避免迁移 + 保留按 status 的 DB 过滤/列表查询）。改为"仅由执行结果写入"的强约束，等价达成审计目标且风险更低。
High 知识库
5. 知识库删除后多处悬空引用
4张表持有 knowledge_base_id CharField: Project / ApiTestCase / Requirement / AIGenerationRecord
删除知识库时仅调用 WeKnora API 删除远端资源，但完全不扫描/清理本地数据库中的引用。删除后 Project.knowledge_base_id、ApiTestCase.knowledge_base_id 等仍指向已不存在的 KB ID。后续使用这些值调用 WeKnora API 会返回 404。
风险: 关联了知识库的项目/用例/需求/AI记录全部分失效；用户体验到"知识库不存在"错误却不知道哪个项目出问题
修复: 删除知识库前扫描所有引用表，生成影响报告；删除时级联 SET_NULL 所有引用或阻止删除
High 测试用例
6. 批量删除模块时跳过用例权限检查
testcase/services/module_service.py:183 — 直接 TestCase.objects.filter(module_id__in=ids).delete()
删除模块时可连带删除模块下的所有用例。但此操作完全跳过权限检查——不验证当前用户对每个用例是否有删除权限（对比 batch_delete_test_cases 会逐个检查 version 权限）。也不检查用例所属版本是否已归档。
风险: 普通成员删除模块时连带删掉管理员创建的用例；归档版本下的用例本应冻结但被连带删除
修复: 逐用例权限检查；归档版本下的模块/用例禁止删除；ApiTestCase 的 module FK 同步 SET_NULL

🟡 中危 (Medium) — 流程缺陷 / 数据漂移

Medium 测试用例
7. 评审轮次无上限 — 无限驳回循环
testcase/services/review_service.py:211 — revision_number 无条件递增，无 MAX_REVISION_COUNT
用例评审可以无限循环：创建→驳回→修改→重提→驳回→...。每轮都保留完整 Review 记录，没有"多次驳回后自动标记为废弃"的机制。
风险: 数据库 Review 表膨胀；无法追踪"共识永远无法达成"的争议用例
修复: 设置 MAX_REVISION_COUNT=5，超限后标记用例为 obsolete 或要求管理员裁决
Medium 测试用例
8. 删除 TestCase 时 AIGenerationRecord 成为孤儿
testcase/models: AIGenerationRecord.test_case FK → on_delete=SET_NULL
删除用例时，关联的 AI 生成记录不会删除（CASCADE vs SET_NULL 策略不一致）。对比 TestCaseReview 和 TestCaseExecution 都是 CASCADE。
风险: 孤儿 AI 记录累积，无法追踪"这个 AI 生成最终产生了什么用例"
修复: 统一为 CASCADE，或删除时提示"N 条 AI 生成记录将保留"
Medium 需求管理
9. 删除需求时无关联用例预警
requirement/models: TestCase.requirement FK → on_delete=SET_NULL
Requirement.delete() 没有覆盖，删除前不检查有多少 TestCase 关联了此需求。需求一删，所有关联用例的 requirement 字段静默变 NULL。测试人员事后发现"需求关联怎么没了"，无法追溯。
风险: 需求追溯链断裂；需求覆盖度统计受影响
修复: Requirement.delete() 覆盖 → 检查关联用例数 → 前端弹窗告警或阻止直接删除
Medium 跨模块
10. ApiTestCase 和 TestCase 的版本/模块 ID 各自独立 已闭环
apitest/models.py + testcase/models: 两者均持有指向同一 TestCaseVersion / TestModule 的 FK，但 ApiTestCase 缺 save() 级版本同步
ApiTestCase（接口测试用例）和 TestCase（手工测试用例）共享同一套版本/模块模型（非完全独立），但 ApiTestCase 此前没有 TestCase 那样的 save() 版本同步逻辑：同一模块下，手工用例已被 #2 强制对齐到模块版本，接口用例的 version 却可能停留在旧值或为空，导致按版本统计时两端对不上。
风险: 跨类型统计口径不一致；测试覆盖率评估失真
已修复（版本一致性）: ApiTestCase.save() 增加与 TestCase #2 完全一致的同步——module 已设置时强制 version = module.version，仅在 module 为空时保留显式版本（不覆盖"未归模块"合法态）。新增管理命令 sync_api_case_versions（支持 --dry-run）回填历史不一致数据。
待业务确认（非缺陷）: 审计原建议的"显式 1:1 对应字段"需以真实业务关系为前提（API 用例与手工用例未必一一对应）。当前两者按版本/模块体系统一归口已实现统计口径一致，未臆造可能误导的死字段；若后续确认需要逐条对应关系，再追加 ApiTestCase.test_case 可选 FK。
