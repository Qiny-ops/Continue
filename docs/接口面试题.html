接口自动化测试面试题库（题目+完整答案）

文档用途：面试复习、自测背诵、面试速查，覆盖初级/中级/高级测试岗位

一、基础理论题（初级 / 中级测试）

1. 什么是接口自动化测试？为什么要做接口自动化，和手工接口测试区别在哪？

答案

1）定义：通过代码/工具自动发起接口请求，自动校验返回结果，无需人工重复操作的接口测试方式。

2）做自动化的原因：

  • 版本迭代快，回归工作量大，手工重复测效率低；
  • 支持夜间/定时批量执行，提前发现缺陷；
  • 可集成CI流水线，提交代码自动校验；
  • 覆盖重复流程、复杂依赖场景，避免人工漏测。

3）和手工接口测试区别：

  • 手工：人工操作Postman/JMeter，单次执行、适合临时探索、新接口初次调试；
  • 自动化：脚本/用例可复用、批量执行、支持持续回归、适合稳定迭代项目，有一定脚本维护成本。

2. 接口自动化适合哪些场景？哪些场景不适合做自动化？

答案

适合场景：

  1. 版本频繁迭代，需要大量回归验证；
  2. 核心业务链路、高频调用接口；
  3. 多环境重复测试（测试/预发）；
  4. 接口依赖复杂、多步骤串联流程；
  5. CI持续集成、定时巡检、线上健康监控。

不适合场景：

  1. 需求频繁改动、接口不稳定、经常改入参/返回结构；
  2. 一次性临时测试、只执行1-2次；
  3. 页面为主、接口极少的小型项目；
  4. 短期即将下线、废弃接口；
  5. 交互逻辑极复杂、变动无规律、维护成本远高于收益。

3. HTTP 常见请求方法 GET/POST/PUT/DELETE 区别，适用业务场景？

答案

  • GET：查询数据，无请求体，参数放url，可缓存、可收藏；适用：查询列表、详情页、下拉数据。
  • POST：新增数据，参数放body，不缓存；适用：注册、下单、提交表单。
  • PUT：全量更新资源；适用：完整修改用户信息、商品完整编辑。
  • DELETE：删除资源；适用：删除订单、删除文件、注销条目。

补充：PATCH为局部更新，行业也常用。

4. 400、401、403、404、405、500、502、503 状态码分别代表什么，接口测试如何排查？

答案

客户端错误（4xx）

  • 400 Bad Request：请求参数非法、格式错误；排查：核对入参类型、JSON格式、字段必填项。
  • 401 Unauthorized：未登录/Token失效；排查：检查鉴权信息、过期时间、登录接口是否正常。
  • 403 Forbidden：登录成功但无权限；排查：账号角色、接口访问权限、越权场景。
  • 404 Not Found：接口地址不存在；排查：url路径、环境域名、接口版本。
  • 405 Method Not Allowed：请求方式错误；排查：接口要求POST却用GET等。

服务端错误（5xx）

  • 500 Internal Server Error：服务代码异常；排查：查看后端日志、参数边界、数据库异常。
  • 502 Bad Gateway：网关/反向代理异常，后端服务宕机；排查：服务是否启动、网关配置。
  • 503 Service Unavailable：服务过载、限流、维护下线；排查：并发量、限流规则、服务状态。

5. Cookie、Token、Session、JWT 区别，自动化中怎么全局携带鉴权信息？

答案

1）区别

  • Session：服务端存储会话，返回SessionId放入Cookie，依赖Cookie；多服务集群需共享Session。
  • Cookie：浏览器本地存储键值对，自动随请求携带，有大小限制。
  • Token：通用鉴权字符串，无状态，可放Header；服务端不用存储会话。
  • JWT：标准化Token，包含头部、载荷、签名，自带用户信息，无需查库校验权限。

2）自动化全局携带方案

  • Postman：全局/环境变量存token，请求头统一配置Authorization: Bearer {{token}}；
  • JMeter：全局HTTP请求头管理器，提取器后置处理器统一提取；
  • Python框架：封装请求基类，登录接口自动保存token，所有请求自动填充Header。

6. 接口请求头 Content-Type：application/json、x-www-form-urlencoded、multipart/form-data 差异，自动化传参注意点？

答案

1）区别

  • application/json：JSON格式，参数放body，后端接收JSON对象；前后端主流。
  • x-www-form-urlencoded：表单键值对，拼接格式k1=v1&k2=v2，适用于普通表单提交。
  • multipart/form-data：支持文件上传，分割分隔符区分参数与文件。

2）自动化注意点

  • Requests：json=传json格式；data=传表单；files=传文件；三者不能混用；
  • Postman：Body面板对应raw/json、x-www-form、form-data，选错直接报400；
  • 必须和后端接口要求的Content-Type保持一致，否则参数接收失败。

7. 接口中入参 query、path、body 参数怎么区分，代码里分别怎么传？

答案

1）区分

  • path（路径参数）：拼接在url路径中，如/user/{id}，id为path参数；
  • query（查询参数）：url?后拼接，如/list?page=1&size=10；
  • body（请求体）：POST/PUT专用，放在请求体内，JSON/表单/文件。

2）requests传参

  • path：字符串格式化url，f"/user/{user_id}"；
  • query：params={"page":1,"size":10}；
  • body：json={} 或 data={}、files={}。

8. 接口依赖是什么？举个业务场景，自动化如何处理接口依赖（A 接口返回数据给 B 接口使用）？

答案

1）接口依赖：后执行接口需要前置接口返回的数据作为入参，存在执行先后顺序。

2）业务场景：登录接口返回token，创建订单接口需要token；创建商品返回goodsId，查询商品需要goodsId。

3）自动化处理方案：

  • Postman：Tests脚本JSON提取器，存入环境变量；
  • JMeter：JSON提取器/正则提取器，后置处理器全局存储；
  • Python/Pytest：登录fixture提前执行，将token、id存入全局变量/缓存，后续用例直接读取。

9. 接口测试断言怎么做？只校验状态码够吗？一般断言哪些内容？

答案

只校验状态码远远不够，状态码200只能代表服务无报错，业务可能返回失败码。

通用断言内容：

  1. 基础：HTTP状态码200；
  2. 业务码：code=0 / success=true；
  3. 返回提示信息msg符合预期；
  4. 核心业务字段存在、字段值符合预期（id、名称、金额）；
  5. 列表长度、分页总条数、数据完整性；
  6. 数据库数据一致性（新增/修改后校验库表）。

10. 接口超时、接口重试机制怎么设计，什么场景需要加重试？

答案

1）超时设计：请求设置timeout（如10s），捕获超时异常，记录日志；区分网络超时、服务响应慢。

2）重试机制：装饰器/循环重试，设置最大重试次数、重试间隔；只对可重试异常触发（超时、502、503限流），400/403参数错误不重试。

3）适用场景：

  • 网络波动偶发超时；
  • 网关限流、服务临时重启502/503；
  • 第三方接口不稳定偶尔调用失败；

不适用：参数错误、权限不足、业务逻辑报错。

二、工具实操类（Postman、JMeter 高频）

1. Postman 如何实现接口自动化？Collection、环境变量、全局变量作用？

答案

自动化实现步骤：

  1. 创建Collection管理接口集合；
  2. 配置环境变量/全局变量存放域名、token、业务ID；
  3. Tests脚本提取返回值实现接口关联；
  4. 设置请求前置脚本统一携带鉴权；
  5. Collection Runner批量执行，导出报告。

三者作用：

  • Collection：批量管理一组业务接口，支持批量运行；
  • 环境变量：区分多环境（测试/预发），仅当前环境生效；
  • 全局变量：所有集合、所有环境共用，生命周期更长，适合全局token。

2. Postman Tests 脚本怎么提取 token、id 等返回值，实现接口关联？

// 解析返回json
let res = pm.response.json();
// 提取token存入环境变量
pm.environment.set("token", res.data.token);
// 提取商品id存入变量
pm.environment.set("goods_id", res.data.goodsId);

后续接口Header直接使用{{token}}，路径/参数使用{{goods_id}}完成关联。

3. Postman 批量执行接口，导出测试报告怎么做？

答案

  1. 打开Collection Runner，选择目标集合、对应环境；
  2. 设置迭代次数、延迟、超时时间；
  3. 运行完成后导出报告：JSON/HTML；
  4. 进阶：Newman命令行执行，集成Jenkins生成标准化报告。

4. JMeter 做接口自动化和压力测试有什么区别？

答案

  • 自动化（功能回归）：线程组线程数=1，1次循环；侧重单接口/业务链路正常返回、数据校验；添加响应断言、JSON断言；无大量并发。
  • 压力测试：多线程、多循环、持续加压；侧重响应时间、TPS、错误率、服务器资源监控；新增聚合报告、服务器性能监控，不侧重精细业务断言。

5. JMeter 正则提取器、JSON 提取器使用场景，二者怎么选？

答案

  • JSON提取器：接口返回标准JSON，优先使用；支持JSONPath多层取值，简洁稳定。
  • 正则提取器：返回HTML、文本、非标准JSON、Header、Cookie等文本格式数据时使用。

选择原则：JSON返回一律JSON提取器，其余文本类用正则。

6. JMeter 全局 token 怎么统一管理，避免每个接口重复登录？

答案

  1. 新增仅一次控制器，内部放登录请求；
  2. 登录后用JSON提取器提取token，存入全局变量；
  3. 全局HTTP信息头管理器统一添加Authorization，引用token变量；
  4. 所有接口自动携带，无需每个接口单独配置。

7. JMeter 接口报错 400、500，你排查步骤是什么？

答案

  1. 查看请求取样器：核对url、请求方式、Content-Type、入参格式；
  2. 查看响应数据：返回错误提示，定位缺失字段/格式错误；
  3. 400：校验参数类型、JSON格式、必填项；
  4. 500：复制请求参数发给后端，查看服务日志，排查空指针、数据库异常；
  5. 检查Header鉴权、环境域名是否正确。

三、Python+Requests 自动化框架核心（市场主流，面试重点）

1. requests 库常用方法：get/post 传参方式，json 参数和 data 参数区别？

答案

  1. get传参：params字典放查询参数；无请求体。
  2. post传参：
    • json={"k":v}：自动设置Content-Type:application/json，后端接收JSON；
    • data={"k":v}：表单格式x-www-form-urlencoded；

核心区别：传JSON对象用json，表单键值对用data，不可混用。

2. 如何封装统一请求工具类（统一处理 url、请求头、token、超时、异常捕获）？

答案

封装思路：

  1. 创建ApiRequest类，初始化base_url、headers、timeout；
  2. 内置统一get/post/put/delete方法；
  3. 方法内自动拼接域名、填充全局token；
  4. 统一捕获超时、连接失败、状态码异常；
  5. 统一打印请求日志、返回JSON结果，异常统一抛出。

3. 接口依赖怎么处理？举代码思路：登录接口获取 token，其他接口自动携带。

答案

  1. 全局变量/单例类存储token；
  2. 封装登录方法，执行后自动更新全局token；
  3. 请求工具类每次发请求自动读取全局token放入headers；
  4. pytest用例：session级fixture登录一次，所有用例复用token。

4. 响应结果是 json 格式，如何提取指定字段做断言？多层嵌套 json 怎么取值？

答案

  • 单层：res.json()["data"]["token"]
  • 多层嵌套：res.json()["data"]["orderInfo"]["orderId"]
  • 工具封装：写通用get_json_value方法，通过jsonpath取值；
  • 断言：assert 提取字段 == 预期值，assert 字段存在。

5. 自动化中异常捕获怎么写？网络超时、接口 500、参数错误如何区分捕获？

答案

  1. 捕获requests.exceptions.Timeout：网络超时；
  2. 捕获requests.exceptions.ConnectionError：连接失败；
  3. 判断响应状态码：response.status_code >=500 服务异常；
  4. 解析返回业务code：code!=0 代表参数/业务错误；

分层捕获不同异常，打印对应日志，区分报错类型。

6. 如何实现接口数据分离？用 yaml/excel 存储用例，好处是什么？

答案

实现：接口地址、入参、预期结果、请求方法全部写入yaml/excel，代码读取文件驱动执行。

好处：

  1. 用例和代码解耦，改参数不用动脚本；
  2. 非测试开发人员可维护用例；
  3. 多组测试数据统一管理，方便批量参数化；
  4. 便于版本管理、用例复用。

7. 什么是数据驱动测试 DDT，写一个简单 ddt 实现接口多组参数测试？

答案

DDT：数据驱动，将测试数据与业务代码分离，一组代码循环执行多组入参。

Python简单实现：ddt库装饰器，@data传入多组参数，自动循环执行用例。

8. 日志模块 logging 在自动化框架中的作用，如何分级打印日志（INFO/ERROR）？

答案

作用：记录请求url、参数、响应、报错堆栈，方便定位失败用例；区分运行信息和错误。

分级：

  • INFO：正常执行流程、请求信息；
  • ERROR：接口报错、断言失败、异常堆栈；

配置日志文件输出、控制台输出，自动按时间分割日志。

9. 自动化测试报告有哪些？Allure、HTMLTestRunner 区别，怎么生成可视化报告？

答案

报告类型：HTMLTestRunner、Allure、ExtentReport、Newman报告。

区别：

  • HTMLTestRunner：简单html，仅展示成功失败，无分类、无步骤；
  • Allure：轻量化可视化，支持用例分类、步骤截图、缺陷分级、筛选，可读性强。

生成：

  • HTMLTestRunner：unittest执行后直接导出html；
  • Allure：pytest执行生成allure原始数据，命令行渲染网页报告。

10. 接口加密场景：请求参数 AES/RSA 加密，返回数据解密，框架怎么封装？

答案

  1. 封装加密工具类：提供AES加密、RSA签名方法；
  2. 统一请求基类内部自动对入参加密后再发起请求；
  3. 响应返回后自动调用解密工具解析返回体；
  4. 密钥、加密模式统一配置在环境配置文件，方便切换。

四、Pytest 测试框架高频面试题

1. pytest 相比 unittest 优势有哪些？

答案

  1. 简洁，无需类、self，函数即可写用例；
  2. 强大fixture替代setup/teardown，作用域灵活；
  3. 原生参数化、跳过、重跑失败用例；
  4. conftest全局共享fixture，不用重复导入；
  5. 丰富插件：allure、pytest-rerunfailures；
  6. 用例执行顺序灵活、支持分层管理。

2. fixture 作用，如何实现全局登录 token fixture，所有用例自动调用？

答案

fixture作用：提供前置/后置操作，数据、鉴权、初始化资源，复用前置逻辑。

全局token实现：

  1. conftest.py定义session级fixture login；
  2. login内部调用登录接口，返回token；
  3. 其他用例函数传入login参数自动执行登录，全局复用token。

3. fixture 的作用域（function/class/module/session）分别适用什么场景？

答案

  • session：整个测试会话只执行一次，全局登录、数据库连接；
  • module：单个py文件执行一次，模块通用数据；
  • class：每个测试类执行一次；
  • function：每个用例执行一次，每次清空临时数据。

4. pytest 参数化几种方式，如何读取 yaml 文件批量参数化接口用例？

答案

参数化方式：@pytest.mark.parametrize、ddt；

yaml批量参数化：封装读取yaml工具，读取多组请求数据，循环传入parametrize。

5. pytest 跳过用例、预期失败、重跑失败用例命令怎么写？

答案

  • 跳过：@pytest.mark.skip(reason="暂不执行")
  • 预期失败：@pytest.mark.xfail
  • 重跑命令：pytest --reruns 2 --reruns-delay 1（失败重跑2次，间隔1s）

6. pytest 钩子函数 conftest.py 作用，为什么不用到处导入 fixture？

答案

conftest.py：pytest全局配置文件，存放公共fixture、钩子函数；

pytest自动识别同目录及上级conftest，用例直接使用fixture名称，无需import导入，简化代码。

7. 如何控制用例执行顺序？接口有强依赖时怎么保证执行先后？

答案

  1. 插件pytest-ordering标记@order；
  2. 强依赖场景：统一放入同一个fixture串行执行，不拆分独立用例；
  3. 不推荐依赖执行顺序写用例，尽量解耦，必须依赖则前置fixture统一处理。

8. Allure 报告常用装饰器（@feature、@story、@severity）使用场景？

答案

  • @feature("用户模块")：一级大模块分类；
  • @story("登录功能")：二级子功能；
  • @severity(allure.severity_level.CRITICAL)：用例优先级（阻断/高/中/低），报告可筛选核心用例。

五、完整自动化框架架构实战题（中级 / 高级测试必问）

1. 说说你搭建的接口自动化框架整体目录结构，每个文件夹作用？

api_auto/
├── api/        # 接口封装层，每个模块接口类
├── cases/      # 测试用例层，pytest用例
├── data/       # 测试数据yaml、环境配置
├── common/     # 公共工具：请求、加密、数据库、日志
├── conf/       # 环境域名、密钥配置
├── reports/    # allure/html报告输出
├── logs/       # 运行日志文件
├── conftest.py # 全局fixture
└── run.py      # 统一执行入口

2. 框架分层设计：请求层、用例层、数据层、公共工具层、报告层，分层意义？

答案

  1. 请求层：统一封装接口调用，隔离http细节；
  2. 用例层：业务测试逻辑、断言，只关心业务；
  3. 数据层：存储参数、环境配置，数据代码分离；
  4. 公共工具层：日志、加密、数据库、文件处理，复用工具；
  5. 报告层：统一输出测试结果；

分层目的：高内聚低耦合，单一职责，便于维护、扩展。

3. 如何实现多环境切换（测试环境、预发、生产），不用修改代码切换地址？

答案

  1. conf目录下多份环境yaml：test.yaml、pre.yaml；
  2. 配置文件存放各环境base_url、数据库地址；
  3. 执行入口通过命令行参数指定环境，动态读取对应配置；
  4. 所有接口自动读取当前环境域名，无需改动业务代码。

4. 数据库校验：接口新增数据后，如何连接 MySQL 查询数据库，断言数据入库正确？

答案

  1. common封装mysql工具类，封装查询、新增方法；
  2. 新增接口执行完成后，调用sql查询对应表；
  3. 取出数据库字段，和接口入参做断言；
  4. 测试结束清理测试脏数据，避免影响其他用例。

5. 接口上传文件、下载文件，requests 如何实现？

答案

  • 上传：files={"file": open("test.jpg","rb")}，post传files参数；
  • 下载：stream=True流式接收response.content，写入本地文件。

6. 定时执行自动化用例怎么做？Jenkins + 定时任务流程讲一遍。

答案

  1. Jenkins新建任务，拉取Git自动化代码；
  2. 配置定时构建（如每日凌晨2点执行）；
  3. 构建步骤：安装依赖、执行pytest生成allure数据；
  4. 构建后生成Allure报告，推送结果至钉钉；
  5. 定时自动执行回归全量接口。

7. Jenkins 集成自动化：代码提交 Git 后自动执行接口测试，发送测试报告到钉钉 / 企业微信，完整流程？

答案

  1. Git仓库配置Webhook，提交代码触发Jenkins；
  2. Jenkins拉取最新代码，安装Python依赖；
  3. 执行pytest自动化用例，生成allure原始数据；
  4. 渲染Allure可视化报告；
  5. 读取执行结果（失败用例数），调用钉钉机器人接口发送摘要+报告链接。

8. 自动化用例失败，自动截图 / 保存接口请求日志，怎么实现？

答案

  1. 请求基类每次请求自动记录url、header、入参、响应体写入日志文件；
  2. pytest钩子函数pytest_runtest_makereport，捕获用例失败；
  3. 失败时将本次完整请求日志单独保存到失败目录，便于复现问题。

9. 接口并发场景，自动化如何处理接口并发报错、脏数据问题？

答案

  1. 每条用例使用唯一隔离数据（随机手机号、随机订单号）；
  2. 测试后通过数据库/接口删除生成的测试数据；
  3. 并发用例加锁、避免共用同一业务资源；
  4. 设计幂等测试数据，重复执行不产生脏数据。

10. 自动化脚本维护成本高，怎么降低维护工作量？

答案

  1. 数据与代码分离，参数统一放yaml；
  2. 统一封装请求、加密、数据库公共方法；
  3. 抽取公共fixture，复用登录、初始化逻辑；
  4. 接口变动只修改api层封装，不改动大量用例；
  5. 规范返回结构，通用断言封装工具方法；
  6. 定期清理废弃用例，区分核心回归用例与临时用例。

六、接口测试场景 & 缺陷类面试题

1. 接口边界值测试怎么做？数字、字符串、空参数、超长参数举例。

答案

  • 数字：最大值、最小值、0、负数、小数、超出整型范围；
  • 字符串：空字符串、全空格、超长文本、特殊符号、emoji；
  • 必填参数不传、传null；
  • 分页参数page=0、page负数、size超大值；

自动化：参数化批量传入边界值用例，批量校验报错提示。

2. 如何做接口异常测试：非法参数、空 token、过期 token、越权访问？

答案

  • 非法参数：传错误类型、缺失必填字段；
  • 空token：Header不传Authorization；
  • 过期token：手动构造过期签名；
  • 越权：A用户token查询B用户订单；

预期均返回401/403或业务错误码，自动化单独编写异常场景用例。

3. 什么是接口幂等性？如何测试接口幂等，自动化怎么设计用例？

答案

1）幂等：同一请求重复提交多次，不会产生多条数据、重复扣款等副作用；

2）测试方式：连续调用同一创建/支付接口3次，校验数据库仅生成1条数据；

3）自动化用例：循环发起多次相同请求，查询数据库校验数据数量。

4. 第三方接口（支付、短信）如何自动化测试，不能调用真实第三方怎么处理？

答案

  1. 测试环境使用Mock服务替代真实第三方；
  2. 搭建本地Mock接口，模拟成功/失败/超时返回；
  3. 通过配置开关切换真实第三方与Mock地址；
  4. 覆盖第三方各类返回场景（成功、余额不足、超时）。

5. 接口返回大量分页数据，自动化如何校验分页逻辑？

答案

  1. 查询第一页，校验page、size、total总条数；
  2. 查询最后一页，校验数据条数小于等于size；
  3. 查询page超出最大页数，返回空列表；
  4. 校验相邻页无重复数据、数据连续不丢失。

6. 测试过程中接口偶尔报错，偶现 bug 怎么定位排查？

答案

  1. 开启完整请求日志，保存每次请求入参、响应；
  2. 加重试机制，复现偶发问题；
  3. 查看服务端日志：并发、数据库锁、限流、超时；
  4. 复现步骤：多次循环执行该用例，增加并发调用；
  5. 区分网络波动、服务性能、代码逻辑缺陷。

七、进阶开发 & AI 相关（含 LangChain 接口）

1. 如何做 AI 大模型接口自动化（LangChain/OpenAI 接口）？和普通业务接口区别？

答案

1）自动化方案：requests封装对话接口，传入prompt，校验返回文本关键词、返回长度；

2）区别：

  • 普通接口：结构化JSON，返回固定字段；
  • LLM接口：多为流式输出，返回文本不固定，无标准业务code；
  • 存在会话上下文，多轮对话依赖历史消息。

2. LLM 接口流式返回 stream 数据，requests 如何接收分段返回内容并断言？

答案

请求添加stream=True，循环迭代response.iter_lines()逐行读取分段数据；拼接完整返回文本，校验关键词、回答长度、是否包含指定输出。

3. LangChain 调用链接口存在上下文依赖，自动化怎么保存会话上下文？

答案

  1. 全局变量存储历史对话message列表；
  2. 每次请求带上完整上下文数组；
  3. 封装对话工具类，自动追加本轮问答，持久化会话数据。

4. 接口性能和自动化区分：自动化侧重功能，压测侧重性能，代码实现有什么不同？

答案

自动化：单线程、精细业务断言、校验数据正确性、集成CI回归；

性能压测：多并发线程、统计TPS/响应时间/错误率，弱化业务细节断言，监控服务器指标。

5. 接口 Mock 是什么？什么时候需要 Mock，pytest 如何 mock 第三方接口？

答案

Mock：模拟第三方接口返回指定数据，隔离外部依赖；

适用场景：第三方不稳定、收费、未开发完成；

pytest实现：使用requests-mock库，拦截指定url，自定义返回JSON。

八、开放问答（面试官收尾必问）

1. 工作中自动化接口用例覆盖率大概多少，哪些接口不会写自动化？

答案

核心业务链路覆盖率80%~90%；

不做自动化：一次性临时接口、即将下线接口、频繁改动的内部调试接口、极低访问频次后台管理接口。

2. 自动化落地遇到过哪些难点，怎么解决的？

答案

常见难点：

  1. 接口频繁变更，维护成本高 → 数据分离、分层封装，减少改动范围；
  2. 依赖第三方不稳定 → Mock替代；
  3. 执行产生脏数据 → 用例隔离、执行后清理数据；
  4. 团队不重视，无人维护 → 接入CI流水线，提交代码自动校验，强制回归。

3. 假如给你一个全新项目，你搭建接口自动化的完整步骤？

答案

  1. 梳理项目接口文档，划分模块；
  2. 搭建基础框架目录、封装请求、日志、配置工具；
  3. 配置多环境文件，统一鉴权处理；
  4. 编写核心业务流程用例，覆盖正常/异常/边界场景；
  5. 接入Allure报告、失败日志保存；
  6. 集成Jenkins定时/提交自动执行；
  7. 配置数据清理机制，输出使用文档，交付团队。

4. 自动化脚本频繁维护，你有什么优化方案？

答案

  1. 数据与代码解耦，用yaml管理参数；
  2. 抽取公共工具、通用fixture，减少重复代码；
  3. 统一接口层封装，接口改动只修改一处；
  4. 标准化返回结构，封装通用断言函数；
  5. 区分核心回归用例与临时用例，定期清理废弃脚本；
  6. 规范接口文档，推动后端稳定接口结构，减少频繁变更。
