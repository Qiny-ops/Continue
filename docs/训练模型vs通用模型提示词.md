# AI 生成测试用例：训练模型 vs 通用模型+提示词

## 一、两种方式对比

| 维度 | 训练模型 | 通用模型+提示词 |
|------|----------|------------------|
| 实现方式 | 使用测试用例数据训练/微调模型 | 通过提示词引导通用模型输出 |
| 适用场景 | 功能测试用例（标准化程度高） | 业务逻辑、边界、安全测试等 |
| 数据依赖 | 需要大量高质量训练数据 | 需要精心设计提示词 |

---

## 二、训练模型的优缺点

### 优点

#### 1. 输出质量稳定

```
训练数据已包含大量符合规范的用例样本
    ↓
模型学习到标准格式和测试思路
    ↓
输出格式统一、字段完整、逻辑清晰
```

**示例：** 训练后的模型能稳定输出：
```json
{
  "title": "用户登录-正常登录",
  "steps": "1. 打开登录页面\n2. 输入用户名和密码\n3. 点击登录按钮",
  "expected_result": "登录成功，跳转首页",
  "priority": "P1",
  "test_type": "功能点测试"
}
```

#### 2. 减少 Prompt Engineering 工作

| 对比项 | 训练模型 | 通用模型+提示词 |
|--------|----------|------------------|
| 提示词长度 | 简短指令即可 | 需要详细的约束、示例、格式说明 |
| 提示词复杂度 | 低 | 高 |
| 调试成本 | 一次性训练成本 | 持续迭代提示词 |

**训练模型提示词：**
```
请为"用户登录"功能生成功能测试用例。
```

**通用模型提示词：**
```
你是一位专业的软件测试工程师。请根据功能点生成测试用例。

## 输出要求
1. 只输出JSON数组，不要输出其他内容
2. 每个用例必须包含：title, steps, expected_result, priority
3. 覆盖正常场景和异常场景
4. 步骤要具体可执行
5. 预期结果要明确可验证
...
（可能需要几百字的约束）
```

#### 3. 领域知识内化

- 模型已学习测试领域的专业术语和最佳实践
- 无需每次都解释"什么是测试步骤"、"什么是预期结果"
- 输出更符合测试人员的思维习惯

#### 4. 推理效率高

| 对比项 | 训练模型 | 通用模型+提示词 |
|--------|----------|------------------|
| 输入 token 数 | 少（简短提示） | 多（长提示词） |
| 推理速度 | 快 | 慢 |
| 成本 | 低（训练一次性投入） | 高（每次都要处理长提示词） |

#### 5. 格式解析成功率高

- 输出格式经过训练已固化
- JSON 格式错误率低
- 减少后处理解析失败的情况

---

### 缺点

#### 1. 训练成本高

| 成本类型 | 说明 |
|----------|------|
| 数据成本 | 需要收集、清洗、标注大量高质量测试用例 |
| 计算成本 | 训练/微调需要 GPU 资源 |
| 时间成本 | 训练周期可能数天到数周 |
| 人力成本 | 需要机器学习工程师参与 |

#### 2. 灵活性差

```
新增测试类型（如性能测试用例）
    ↓
需要重新收集该类型的训练数据
    ↓
重新训练或微调模型
    ↓
周期长、成本高
```

#### 3. 更新维护困难

| 场景 | 训练模型 | 通用模型+提示词 |
|------|----------|------------------|
| 调整输出格式 | 重新训练 | 修改提示词 |
| 新增字段 | 重新训练 | 修改提示词 |
| 修复问题 | 重新训练 | 修改提示词 |
| 适配新场景 | 重新训练 | 修改提示词 |

#### 4. 长尾场景覆盖不足

- 训练数据可能未覆盖所有边界场景
- 遇到训练数据外的场景可能输出不稳定
- 需要持续收集新场景数据并重新训练

#### 5. 过拟合风险

- 模型可能过度学习训练数据的模式
- 输出可能过于"模板化"，缺乏针对性
- 对特殊业务场景的适应性下降

---

## 三、通用模型+提示词的优缺点

### 优点

#### 1. 灵活性强

```
需求变化
    ↓
修改提示词（分钟级）
    ↓
立即生效
```

**示例：** 新增"性能测试用例"生成能力

```python
# 只需新增一个提示词模板
PERFORMANCE_TEST_PROMPT = """
请为{module}模块的{func_point}功能生成性能测试用例。
关注：响应时间、并发能力、资源占用。
输出格式：...
"""
```

#### 2. 无需训练成本

| 对比项 | 训练模型 | 通用模型+提示词 |
|--------|----------|------------------|
| 数据准备 | 需要 | 不需要 |
| 模型训练 | 需要 | 不需要 |
| GPU资源 | 需要 | 不需要 |
| 启动周期 | 周级 | 小时级 |

#### 3. 覆盖面广

- 通用模型知识面广，能处理多种场景
- 不受训练数据范围限制
- 适合覆盖边界测试、安全测试、异常测试等多样化场景

#### 4. 快速迭代

```
发现问题 → 修改提示词 → 测试验证 → 立即上线
（周期：小时到天）
```

vs

```
发现问题 → 收集数据 → 清洗标注 → 重新训练 → 测试验证 → 上线
（周期：周到月）
```

#### 5. 场景适应性强

- 通过调整提示词可快速适配不同业务场景
- 同一模型可用于多种测试类型
- 提示词可针对具体需求定制

---

### 缺点

#### 1. 输出质量不稳定

**问题1：格式不稳定**

```
第1次输出：
{"title": "登录测试", "steps": "...", "expected_result": "..."}

第2次输出：
登录测试用例：
标题：登录测试
步骤：...
预期：...

第3次输出：
```json
{"testpoint": "登录测试", ...}  // 字段名不一致
```
```

**问题2：内容不稳定**

- 同一功能点，每次生成的用例数量可能不同
- 测试场景覆盖可能遗漏
- 用例详细程度不一致

#### 2. Prompt Engineering 成本高

| 工作内容 | 说明 |
|----------|------|
| 设计提示词 | 需要反复调试，找到最优表达 |
| 添加约束 | 防止模型输出不符合要求的内容 |
| 提供示例 | few-shot 示例引导正确输出 |
| 格式说明 | 详细说明 JSON 结构和字段要求 |
| 迭代优化 | 根据输出结果持续调整 |

**一个成熟的提示词可能需要：**
- 几百到几千字的约束说明
- 多个 few-shot 示例
- 反复迭代调优（可能数十次）

#### 3. Token 消耗大

| 对比项 | 训练模型 | 通用模型+提示词 |
|--------|----------|------------------|
| 系统提示词 | 50-100 tokens | 500-2000 tokens |
| 每次调用成本 | 低 | 高 |
| 批量调用成本 | 显著更低 | 显著更高 |

#### 4. 推理效率低

- 每次都要处理长提示词
- 响应时间更长
- 并发处理能力受限

#### 5. 依赖提示词质量

```
提示词质量差 → 输出质量差
    ↓
需要专业的 Prompt Engineer
    ↓
人才成本
```

## 四、项目中的混合策略

### 策略设计

```
测试用例需求
    ↓
    ├── 功能测试用例 → 训练模型（标准化程度高、复用性强）
    │
    └── 其他测试用例 → 通用模型+提示词（灵活性要求高）
        ├── 业务逻辑测试
        ├── 边界测试
        ├── 安全测试
        └── 性能测试
```

### 为什么这样设计？

| 测试类型 | 特点 | 选择方案 | 原因 |
|----------|------|----------|------|
| 功能测试 | 场景标准、格式统一 | 训练模型 | 质量稳定、效率高 |
| 业务逻辑测试 | 场景多样、与业务强相关 | 提示词 | 灵活适配不同业务 |
| 边界测试 | 场景多、变化快 | 提示词 | 快速迭代 |
| 安全测试 | 专业性强、更新快 | 提示词 | 无需重新训练 |

### 具体实现

```python
async def generate_testcases(self, module, func_point, test_directions):
    all_cases = []
    
    for direction in test_directions:
        if direction == "功能点测试":
            # 使用训练模型
            cases = await self.trained_model.generate(module, func_point)
        else:
            # 使用通用模型+提示词
            prompt = get_prompt_for_direction(direction)
            cases = await self.general_model.generate(module, func_point, prompt)
        
        all_cases.extend(cases)
    
    return all_cases
```

## 五、决策建议

### 选择训练模型的场景

| 场景 | 原因 |
|------|------|
| 用例格式高度标准化 | 模型可学习固定模式 |
| 用例量大且重复性高 | 训练成本可摊薄 |
| 对输出质量要求高 | 训练后更稳定 |
| 有充足的训练数据 | 数据是训练的前提 |
| 场景相对固定 | 减少重新训练频率 |

### 选择通用模型+提示词的场景

| 场景 | 原因 |
|------|------|
| 需求变化频繁 | 提示词可快速调整 |
| 场景多样化 | 无需为每种场景训练 |
| 缺乏训练数据 | 不依赖训练数据 |
| 快速验证阶段 | 启动成本低 |
| 专业领域测试 | 通过提示词注入领域知识 |

### 混合策略建议

```
1. 核心场景（功能测试）
   → 投入训练成本，获得稳定输出

2. 长尾场景（边界、安全、性能）
   → 使用提示词，保持灵活性

3. 新场景探索
   → 先用提示词验证
   → 场景成熟后再考虑训练
```
