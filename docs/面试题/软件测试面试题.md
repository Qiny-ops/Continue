## 一、测试理论基础

### 1.1 测试用例设计

**Q1: 请设计一个用户登录功能的测试用例**

**参考答案：**

首先，我会从功能完整性角度出发，设计正常场景的测试用例。在本项目中，登录功能是整个系统的入口，我设计了以下正常场景：
- 使用正确的用户名和密码登录，验证登录成功后跳转到首页
- 验证Token正确存储在本地存储中
- 验证用户信息正确显示

其次，我会从异常处理角度出发，设计异常场景的测试用例。根据我在本项目中的实际测试经验，发现了以下需要验证的场景：
- 用户名为空、密码为空
- 用户名不存在、密码错误
- 用户名包含特殊字符（如SQL注入字符）
- 账户被禁用状态
- 连续多次登录失败（暴力破解防护）

最后，我会从边界值角度出发，设计边界测试用例：
- 用户名最大长度（本项目为50字符）
- 密码最小长度（本项目为6字符）
- 密码最大长度（本项目为20字符）

**为什么这样设计？** 因为登录功能涉及安全性，必须覆盖所有可能的攻击向量。在本项目中，我通过安全测试发现了弱密码验证缺失的问题，这证明了全面测试用例设计的重要性。

**Q2: 什么是测试金字塔？请结合本项目说明**

**参考答案：**

首先，测试金字塔是一种测试策略模型，它建议测试应该呈现金字塔形状：底层是大量的单元测试，中间是适量的集成测试/API测试，顶层是少量的端到端测试。

其次，在本项目中，我实践了测试金字塔理论：
```
        /\
       /UI\        - UI测试：7个用例，执行时间52.8s
      /------\
     /  API   \     - API测试：16个用例，执行时间43.81s
    /----------\
   /  单元测试  \   - 单元测试：各模块函数级测试
  /--------------\
```

最后，我选择这种分层策略的原因是：
- **单元测试**执行最快，可以快速发现代码级别的问题
- **API测试**验证业务逻辑，执行速度适中，维护成本较低
- **UI测试**模拟真实用户操作，但执行慢、维护成本高

**深度思考：** 在实际项目中，我发现API测试的性价比最高。43.81秒可以验证16个核心接口，而UI测试52.8秒只能验证7个场景。因此在CI/CD流程中，我优先运行API测试，UI测试则用于关键流程验证。

### 1.2 测试分类

**Q3: 解释冒烟测试、回归测试、集成测试的区别**

**参考答案：**

首先，**冒烟测试**是对系统基本功能的快速验证。在本项目中，每次构建后我会运行冒烟测试，验证以下核心功能：
- 用户能否正常登录
- 项目列表能否正常显示
- 测试用例列表能否正常加载

如果冒烟测试失败，说明系统基本功能受损，不需要进行后续测试。

其次，**回归测试**是验证代码修改后原有功能是否正常。在本项目中，我设计了全量API测试用例作为回归测试套件。每当开发人员修复Bug或添加新功能后，我会运行完整的回归测试，确保修改没有引入新的问题。

最后，**集成测试**是验证模块间交互是否正常。在本项目中，前后端集成测试是重点：
- 验证前端Vue3应用与后端Django API的交互
- 验证数据库操作的正确性
- 验证认证Token的传递机制

**实际经验：** 在项目中，我发现了一个典型的集成问题：前端发送的请求头格式与后端期望不一致，导致认证失败。这个问题只有在集成测试中才能发现，单元测试无法覆盖。

- `@pytest.mark.parametrize`：数据驱动测试
- `allure-pytest`：生成美观的测试报告
- `pytest-xdist`：并行执行测试

**实际收益：** 在本项目中，使用Pytest后：
- 测试代码量减少约30%
- 测试执行时间从60秒降到43秒（通过session级别Fixture复用登录）
- 测试报告更加直观，便于问题定位

### 2.2 代码实现

**Q6: 请实现一个BaseAPI类，封装通用的HTTP请求方法**

**参考答案：**

首先，我会设计BaseAPI类的核心功能，包括请求发送、响应处理、认证管理：

```python
import requests
import logging

class BaseAPI:
    def __init__(self, base_url: str):
        self.base_url = base_url.rstrip('/')
        self.session = requests.Session()
        self.token = None
        self.headers = {
            'Content-Type': 'application/json',
            'Accept': 'application/json'
        }

    def set_token(self, token: str):
        """设置认证Token"""
        self.token = token
        self.headers['Authorization'] = f'Bearer {token}'

    def request(self, method: str, endpoint: str, **kwargs):
        """统一请求方法"""
        url = f"{self.base_url}{endpoint}"
        kwargs.setdefault('headers', self.headers)
        
        # 记录请求日志
        logging.info(f"Request: {method} {url}")
        
        response = self.session.request(method, url, **kwargs)
        return self._handle_response(response)

    def _handle_response(self, response):
        """统一响应处理"""
        try:
            data = response.json()
        except:
            data = {'raw_text': response.text}
        
        return {
            'status_code': response.status_code,
            'code': data.get('code'),
            'message': data.get('message'),
            'data': data.get('data'),
            'success': response.status_code == 200
        }

    def get(self, endpoint, params=None):
        return self.request('GET', endpoint, params=params)

    def post(self, endpoint, data=None):
        return self.request('POST', endpoint, json=data)
```

其次，我设计`_handle_response`方法的原因是：
- **统一响应格式**：无论后端返回什么格式，测试代码都能用统一方式访问
- **错误处理**：捕获JSON解析异常，避免测试因响应格式问题崩溃
- **日志记录**：便于调试和问题追踪

最后，使用Session对象而不是直接使用requests的原因是：
- **连接池复用**：减少TCP连接建立的开销
- **Cookie管理**：自动处理Cookie
- **性能提升**：在本项目中，使用Session后API测试执行时间减少了约15%

## 三、UI自动化测试

### 3.1 框架设计

**Q9: 什么是Page Object Model？为什么要使用它？**

**参考答案：**

首先，Page Object Model（POM）是一种设计模式，它将页面元素和操作封装成类。核心思想是：**页面是对象，元素是属性，操作是方法**。

其次，在本项目中，我使用POM重构了测试代码，对比效果明显：

```python
# 不使用POM - 元素定位散落在测试代码中
def test_login(page):
    page.fill('input[name="username"]', 'admin')
    page.fill('input[name="password"]', 'password')
    page.click('button[type="submit"]')
    assert 'dashboard' in page.url

# 使用POM - 元素定位集中管理
class LoginPage:
    def __init__(self, page):
        self.username = 'input[name="username"]'
        self.password = 'input[name="password"]'
        self.submit = 'button[type="submit"]'
    
    def login(self, username, password):
        self.page.fill(self.username, username)
        self.page.fill(self.password, password)
        self.page.click(self.submit)

def test_login(page):
    login_page = LoginPage(page)
    login_page.login('admin', 'password')
    assert 'dashboard' in page.url
```

最后，POM带来的实际收益：
- **维护成本低**：当页面元素变化时，只需修改Page类，测试用例无需改动
- **代码复用高**：登录操作在多个测试中复用
- **可读性强**：`login_page.login('admin', 'password')`比原始代码更易理解

**深度思考：** 在本项目中，前端开发修改了登录按钮的选择器，从`button[type="submit"]`改为`button.login-btn`。由于使用了POM，我只需要修改`LoginPage`类中的一个常量，所有测试用例自动生效。

**Q11: 请实现一个登录页面的Page Object类**

**参考答案：**

首先，我会设计LoginPage类的元素定位器和基本方法：

```python
from playwright.sync_api import Page
from pages.base_page import BasePage

class LoginPage(BasePage):
    def __init__(self, page: Page):
        super().__init__(page)
        # 元素定位器 - 集中管理
        self.username_input = 'input[placeholder*="用户名"]'
        self.password_input = 'input[placeholder*="密码"]'
        self.login_button = 'button[type="submit"]'
        self.error_message = '.el-message--error'
        self.remember_checkbox = 'input[type="checkbox"]'

    def navigate_to_login(self):
        """导航到登录页面"""
        self.navigate('/login')

    def login(self, username: str, password: str, remember: bool = False):
        """执行登录操作"""
        self.fill(self.username_input, username)
        self.fill(self.password_input, password)
        
        if remember:
            self.check(self.remember_checkbox)
        
        self.click(self.login_button)

    def get_error_message(self) -> str:
        """获取错误提示信息"""
        if self.is_visible(self.error_message):
            return self.get_text(self.error_message)
        return ''

    def is_login_page(self) -> bool:
        """判断是否在登录页面"""
        return self.is_visible(self.login_button)
```

其次，我设计`is_login_page()`方法的原因是：
- 在测试中验证页面跳转是否正确
- 作为其他测试的前置条件检查

最后，我使用模糊匹配选择器`placeholder*="用户名"`的原因是：
- 更健壮，即使placeholder文字有细微变化也能匹配
- 在本项目中，前端开发曾将"用户名"改为"请输入用户名"，使用模糊匹配后测试无需修改

其次，我会分析动态加载的原因：

- **前端渲染**：使用`wait_for_selector()`
- **动画效果**：使用`wait_for_function()`

最后，对于复杂的等待场景，我会封装通用的等待函数：

```python
def wait_for_condition(page, selector, condition, timeout=10000):
    """轮询等待条件满足"""
    start = time.time()
    while time.time() - start < timeout / 1000:
        if condition(page.locator(selector)):
            return True
        page.wait_for_timeout(100)
    return False
```

**实际经验：** 在本项目中，项目列表页面使用了懒加载，初次加载只显示20条数据。我使用`wait_for_selector('.project-item')`确保数据加载完成后再进行断言。

**Q15: 解释以下性能指标**

**参考答案：**

首先，我会解释核心指标的含义：

**响应时间（Response Time）**：从发送请求到收到响应的时间。
- 本项目：平均2055ms
- 建议：<200ms
- 差距原因：使用开发服务器，无缓存，数据库查询未优化

**吞吐量（Throughput/RPS）**：单位时间内处理的请求数。
- 本项目：约0.5 RPS
- 建议：>100 RPS
- 计算方式：总请求数 / 总时间

```python
import pytest
import allure

@allure.feature('安全测试')
class TestSQLInjection:
    
    @pytest.mark.security
    @pytest.mark.parametrize('payload', [
        "' OR '1'='1",           # 经典注入
        "' OR '1'='1' --",       # 注释绕过
        "admin'--",              # 用户名注入
        "1' OR '1' = '1",        # 数字注入
        "'; DROP TABLE users; --", # 危险操作
    ])
    def test_sql_injection_login(self, base_url, session, payload):
        """测试登录接口SQL注入"""
        response = session.post(
            f'{base_url}/users/login/',
            json={'username': payload, 'password': payload}
        )
        
        # 验证：应该返回401或400，不应该返回200
        assert response.status_code in [400, 401], \
            f'SQL注入可能成功，payload: {payload}'
        
        # 验证：不应该返回用户数据
        if response.status_code == 200:
            data = response.json()
            assert 'token' not in data.get('data', {}), \
                'SQL注入成功获取了Token'
```

其次，我会解释测试逻辑：
- 使用参数化测试覆盖多种攻击载荷
- 验证响应状态码，注入攻击应该失败
- 验证响应内容，确保没有泄露敏感数据

最后，我会说明本项目的测试结果：
- Django ORM默认使用参数化查询，SQL注入风险较低
- 但仍需验证，防止开发人员使用原生SQL

**深度思考：** 安全测试不能只依赖自动化，还需要人工审查代码。在本项目中，我通过代码审查发现了潜在的注入风险点。
